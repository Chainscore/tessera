## Content

- Iterations for state root update (2)

## Iteration 1 State Update Flow (Proposed)

```mermaid
flowchart TD
    A([Start Update State]) --> B[Load whole tree from RAM]
    B --> C[Begin recursive update update_tree]

    subgraph RECURSIVE_UPDATE [Recursive Node Update]
      C --> D{Current Node Type?}

      D -- "Empty" --> E[Create new leaf node - Encode leaf with key & value]
      E --> F[Compute hash for new leaf node]
      F --> G[Return leaf node hash & structure]

      D -- "Leaf" --> H{Does key match?}
      H -- Yes --> I[Update leaf node - Encode new leaf with new value]
      I --> J[Compute hash for updated leaf]
      J --> G
      H -- No --> K[Conflict on leaf: Split branch into two leaf nodes]
      K --> L[Call merkelize_recursive on both key-value pairs]
      L --> M[Compute new branch hash for split branch]
      M --> G

      D -- "Branch" --> N{Determine bit at current bit_index}
      N -- "Bit = 0" --> O[Traverse left child]
      N -- "Bit = 1" --> P[Traverse right child]

      O --> Q[Recursively update left subtree]
      Q --> R[Receive updated left child hash & structure]

      P --> S[Recursively update right subtree]
      S --> T[Receive updated right child hash & structure]

      R & T --> U[Encode branch node with new left & right hashes]
      U --> V[Compute new branch node hash]
      V --> G
    end

    G --> W{Is current node the root?}
    W -- No --> X[Return new node hash to parent's update call]
    W -- Yes --> Y[Update the global state_root key in DB]
    Y --> Z([Update Complete]) 
```

## Pros

- **Efficient Localized Updates:**  
  - The update process recalculates only the branch from the modified leaf up to the root, reducing computational overhead.
  - The recursive approach cleanly separates handling of empty, leaf, and branch nodes.

- **Strong Integrity and Persistence:**  
  - Cryptographic hashing (e.g., Keccak-256) ensures that the global state root is a secure commitment to the entire state.
  - Integration with a persistent key‑value store guarantees durability and consistency over restarts.

- **Modularity and Clarity:**  
  - A clear conditional structure for node updates (e.g., matching keys, conflict resolution via branching) improves code readability and maintainability.
  - Clear separation of concerns makes it easier to understand, test, and extend the update logic.

- **Deterministic State Root Updates:**  
  - By propagating updated hashes up to the root, the system deterministically updates the global state root, which is crucial for state verification by other nodes.

## Cons

- **Memory Consumption and Scalability:**  
  - **Full In‑RAM Loading:** Loading the entire trie from RAM may become a resource bottleneck for very large state tries.
  - **In‑Memory vs. On‑Disk Trade-offs:** If the tree exceeds available RAM, accessing nodes from disk could impact performance.

- **Recursive Implementation Challenges:**  
  - **Stack Depth Limitations:** Deep recursion (up to 256 levels in worst-case scenarios) may lead to stack overflow issues in some languages (e.g., Python) unless handled carefully.
  - **Conflict Resolution Overhead:** Splitting a leaf into a branch when conflicts occur can be complex and may introduce performance overhead.

- **Concurrency and Consistency Management:**  
  - **Concurrent Updates:** The design does not inherently address the potential conflicts when multiple updates occur concurrently in overlapping paths. Additional locking or transaction batching may be required.
  - **Failure Recovery:** If an update fails partway through the recursion, the tree could be left in an inconsistent state unless robust rollback mechanisms are in place.

- **Persistent Database Write Overhead:**  
  - **Frequent Node Updates:** Re-encoding and persisting affected nodes for every update can be expensive in high-throughput scenarios.
  - **Complexity in DB Schema Mapping:** Maintaining an up-to-date mapping between in‑memory trie nodes and their persisted counterparts adds complexity to the implementation.
