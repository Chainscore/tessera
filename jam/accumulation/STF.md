# Accumulation

The Accumulation phase in the JAM protocol is responsible for processing work reports and updating the on‐chain state accordingly. It involves several interrelated sub-processes that together ensure that the work outputs generated by the in‑core computation are correctly integrated into the state. The key sub-processes are:

- **Sequential Accumulation**
- **Parallel Accumulation**
- **Single‑Service Accumulation (Δ₁)**
- **Deferred Transfers and State Integration**
- **Preimage Integration**

Below is a detailed description of each component.

---

## SequentialAccumulation

**Function Name:** `SequentialAccumulation`

**Description:**  
This function implements the outer accumulation function (denoted as Δ⁺ in the paper). It processes a set of work reports sequentially, executing the Accumulate logic for each service’s work outputs. The sequential nature is necessary because:

- **Gas Consumption Determination:**  
  The actual gas used by a work item can only be known after its accumulation, which may be less than its advertised gas limit.
  
- **PVM Setup Cost Amortization:**  
  Aggregating work items from the same service into a single PVM invocation helps amortize the fixed cost of setting up the PVM, improving efficiency.
  
- **State Consistency:**  
  Sequential execution guarantees that state updates occur in a well-defined order, ensuring that each work report’s effects are applied correctly.

**Arguments:**

- `gas_limit (Gas)`: The total gas available for the accumulation process.
- `work_reports (WorkReports)`: A collection of work reports that are ready to be accumulated.
- `partial_state (stateContext)`: The state before accumulation, which includes delta(service accounts), iota(validator keys), xi(authorizer keys), and chi(privileges).
- `freeAccServices (ChiG)`: A dictionary of services (by service index) that are set up for free accumulation along with their basic gas allowances.

**Returns:**  
A tuple `(int, State, DeferredTransfers, AccOutputs)` where:
- **Integer**: Number of work results successfully accumulated.
- **Partial State**: The updated state after applying accumulation.
- **DeferredTransfers**: A list of transfers that are deferred to be applied later.
- **AccOutputs**: A mapping of service indices to their corresponding accumulation outputs.

---

## ParallelAccumulation (Δ*)

**Objective:**  
The parallel accumulation function (denoted as Δ*) processes work reports in a non‑sequential, service‑aggregated manner. It enables multiple work items belonging to the same service to be accumulated in a single PVM invocation, thereby maximizing throughput and efficiently amortizing the setup cost.

**Input & Transformation:**  
- **Inputs:** An initial state-context, a sequence of work reports, and a dictionary mapping service indices to their free accumulation gas limits.
- **Transformation:**  
  Δ* uses the single‑service accumulation function (Δ₁) to process work items for each service. It computes the total gas used in PVM execution and aggregates the outputs (accumulation results) and deferred transfers.
- **Output:**  
  Returns a tuple of the total gas consumed, the updated state-context, the list of deferred transfers, and a mapping of service indices to accumulation outputs.

---

## Single‑Service Accumulation (Δ₁)

**Objective:**  
Δ₁ is the core function that “wrangles” work items for a single service from a set of work reports and executes the corresponding PVM (Polka Virtual Machine) invocation to process these items.

**Inputs:**  
- **Initial State-Context (U):** Contains the current mutable state components (service accounts, upcoming validator keys, authorization queue, privileges).
- **Work Reports (⟦W⟧):** A sequence of work reports related to a particular service.
- **Gas Dictionary (D⟨NS → NG⟩):** Provides the gas privileges for each service.
- **Service Index (NS):** The specific service for which the accumulation is performed.

**Processing:**  
- It extracts the work items corresponding to the service from the provided work reports.
- It invokes the Accumulation PVM function (ΨA) with these work items along with contextual information (such as the block’s timeslot and service-specific gas limits).
  
**Returns:**  
A tuple containing:
- The updated state-context after processing the service’s work items.
- A sequence of deferred transfers (if any) resulting from the accumulation.
- The accumulation output (if any) produced by the PVM invocation.
- The actual gas consumed by the service’s accumulation.

**Variables in the Context of a Test Case:**  
- **`o`**: Represents the current PVM state (including the service account’s code and current runtime parameters).
- **`w`**: The subset of work reports (or work items) for the given service.
- **`f`**: Gas-privileges or any other fee parameters associated with the service.
- **`s`**: The service index (e.g., the ID of the service whose work items are being processed).
- **`g`**: The gas limit allocated for processing the work items for the service.
- **`p`**: A rephrased sequence of operand tuples extracted from the work items.

The function Δ₁ ultimately transforms these inputs into a new state-context, a set of deferred transfers, an accumulation output for the service, and a record of the gas used.

## Deferred Transfers and State Integration

**Objective:**  
After work reports are accumulated, some work items may imply transfers (e.g., updating balances between services). This phase integrates those deferred transfers into the service accounts state.

**Process:**
- **Deferred Transfers (T):**  
  A transfer includes information like the sender’s service index, the receiver’s service index, the balance to be transferred, a memo, and a gas limit.
  
- **Selection Function (R):**  
  R takes the sequence of deferred transfers and maps them to each destination service index. It orders transfers primarily by the source service index and secondarily by their order within the sequence.
  
- **State Update:**  
  The intermediate service state (δ†) is updated by applying the deferred transfers via a PVM invocation (ΨT), resulting in a new state (δ‡) where the transfers have been incorporated.

**Output:**  
- The updated state of service accounts after applying deferred transfers.
- This updated state is used in subsequent stages of state transition (e.g., for calculating the accumulation commitment).

---

## Preimage Integration

**Objective:**  
In the preimage integration phase, the protocol integrates preimages provided in the lookup extrinsic into the service state. These preimages are associated with keys that were requested by services (e.g., to fetch external data).

**Process:**
- **Lookup Extrinsic (EP):**  
  A sequence of pairs of service indices and data (octet strings) that represent the preimages. These pairs are ordered and should be unique.
  
- **Validation:**  
  For each pair, the protocol checks if the corresponding preimage is not already in the service state. This involves verifying that the hash of the preimage matches the expected hash and that the preimage has not been superseded.
  
- **State Update:**  
  The service state (initially δ‡ after deferred transfers) is updated to incorporate the new preimages. For each valid preimage pair, the dictionary for preimages is updated at the key derived from the hash. Additionally, metadata (such as the current timeslot) is recorded.
  
**Output:**  
- The final updated service state (δ′), which now includes the integrated preimages, ensuring that all external data needed for service execution is available in the state.

---

## Summary

The Accumulation phase transforms a set of work reports and associated state into an updated state by:
- **Sequentially** processing work reports to determine actual gas usage and updating the state accordingly.
- **In parallel**, aggregating work items for the same service to optimize performance.
- **Using the Single‑Service Accumulation (Δ₁)** function to process work items for each service.
- **Applying deferred transfers** to update balances and other state elements.
- **Integrating preimages** from the lookup extrinsic into the final state.

Together, these steps ensure that all work outputs from the in‑core computation are securely and efficiently integrated into the JAM chain state.
